### 2.5 ★ 真实 FUSE 下的一个隐患：镜像必须能跨启动自愈（已验证成立）

**背景**：AppImage 经 FUSE 挂载，挂载点（`/tmp/.mount_XXXXXX`）是**临时的，退出即卸载**。
而 `snowluma-runtime-mirror` 会在用户主目录建一堆**指向那个挂载点**的软链。
于是第二次启动时挂载点路径就变了 → 上一次留下的软链**全部悬空** →
如果镜像不自我修复，**SnowLuma 第二次启动就找不到 `native/` 里的原生件**。

这个问题在 extract-and-run 模式下**永远不会出现**（解到固定目录），
只有真实 FUSE 才会暴露 —— 又是一个"本地测不出来"的场景。

**实测结果**（`_ql_wsl_fuse_mirror_test.sh`，连续两次真实 FUSE 启动）：

```
第 1 次挂载点: /tmp/.mount_QQ-AgeAiKcIg/opt/qq-agent/resources/app/snowluma/native
              ✓ 软链目标可解析
  停止应用 → 挂载卸载 → 软链悬空（预期现象）
第 2 次挂载点: /tmp/.mount_QQ-AgelBjAci/opt/qq-agent/resources/app/snowluma/native
              ✓ 软链已被重新指向新挂载点，目标可解析
```

**结论：自愈成立。** 补丁里的 `ensureSnowlumaRuntimeMirror` 会逐个比对软链目标，
"目标不符就 unlink 重建"，所以挂载点变化不影响它。

> 这是设计时**没预料到、但恰好成立**的性质 —— 记在这里，因为将来若有人"优化"掉
> 那段"目标不符就重建"的逻辑，AppImage 的第二次启动就会坏。

### 2.7 ★ rpm 依赖解析验证 —— 填补了「依赖未被真实验证」的缺口

**问题**：rpm 冒烟在 Ubuntu 上只能 `rpm -i --nodeps`（Ubuntu 没有 rpm 依赖库），
所以「这条 Requires 到底合不合理」**从来没被验证过** —— 冒烟报告里那条警告指的就是它。
而 rpmbuild **自动生成了 88 条 soname / 版本化符号依赖**（如
`libstdc++.so.6(GLIBCXX_3.4.29)(64bit)`、`libc.so.6(GLIBC_2.34)(64bit)`），
这些在**较老的发行版上很可能找不到提供者** —— 机器上真有一条 `libstdc++.so.6(GLIBCXX_3.4.29)(64bit)`，
不验一下就是不放心。

**不需要一台 RHEL 机器**：Ubuntu 源里就有 **dnf**（Fedora/RHEL 用的那个解析引擎）。
配一份目标发行版的 repo 元数据，就能对**目标架构**做完整解析（纯解析，不装系统）。

`test/50-rpm-deps-resolve.sh` 的结果：

| 目标 | arm64 | x86_64 |
|---|---|---|
| Fedora 44 | ✅ 177 个包 | ✅ 178 个包 |
| **CentOS Stream 9（RHEL 9 上游）** | ✅ 187 个包 | ✅ 189 个包 |
| **Rocky Linux 9（RHEL 9 重建）** | ✅ 187 个包 | ✅ 189 个包 |

**这让文档里那句「RHEL / Rocky / AlmaLinux / Fedora」的支持范围有了证据** ——
连我原先担心的版本化符号要求在企业版上也能满足。

顺带核实了一条容易踩的：包**要求** `libffmpeg.so()(64bit)`（因为 Electron 自带它），
而包**同时提供了**它 —— 是自满足的，无害。若不提供，这个 rpm 就**永远装不上**。

**过程中踩到并修掉的两件事**：

1. **`set -e` 让脚本静默退出**：`lib.sh` 里有 `set -e`，而 `dnf --assumeno`
   在**成功解析之后必然返回 1**（主动放弃事务）→ 脚本当场退出，
   **exit=1、零报错**，看起来像"莫名其妙死了"。修法：`set +e` 包住 dnf 调用。
   这条已写进 `lib.sh` 顶部的注释，提醒后来人。
2. **镜像 429 被误判成依赖问题**：Rocky 原先用 USTC 镜像，它**限流返回 429**，
   元数据没拉下来 → dnf 报成 `nothing provides gtk3/libX11…`，
   **看起来像依赖缺陷，其实是环境问题**。修法：逐个预检每个 repo 的 `repomd.xml`，
   不可达就明确报"环境问题"并跳过；同时换用两个仓库都 200 的 aliyun。
   （这正是「测试自己也会骗人」的又一例。）

## 4. 本轮发现的 8 个问题（全部是"真跑才暴露"）

> 另有 2 条是**测试自身**的缺陷，分别记在 §2.3（两份报告互相覆盖）
> 与 §2.6（判据误报）—— 它们同样值得记，因为「测试写错」和「代码写错」一样会误导人。

### 4.1 ★ drvfs 的 777 会变成包内「全局可写文件」（安全问题）

**现象**：在 `/mnt/f` 上解包运行时，权限全是 `777`（74+ 个文件），包括 `chrome-sandbox`
和所有 `.so`；`cp -a` 把失真模式带进 stage 树，再打进包。

**危害**：**root 拥有但全局可写**的文件装进 `/opt` —— 任何本地用户都能篡改程序代码。
这不是洁癖，是实打实的提权面。

**根因**：Windows 的 `/mnt/e`、`/mnt/f`（drvfs）不支持 POSIX 权限，一律显示 777。

**修法**（两处）：
1. `03-stage.sh` 新增 **5b 权限归一化**：目录 755 / 文件 644 / 可执行白名单 755 /
   `chrome-sandbox` 4755。白名单从「**在 ext4 上**从官方压缩包干净解包」实测得到：
   - Electron（两架构一致，8 个）：`electron`、`chrome-sandbox`、`chrome_crashpad_handler`、
     `libEGL.so`、`libGLESv2.so`、`libffmpeg.so`、`libvk_swiftshader.so`、`libvulkan.so.1`
   - SnowLuma（两架构一致，2 个）：`node`、`launcher.sh`（`native/*.node|.so` 是 644，dlopen 不需要执行位）
2. `test/05-arch-audit.sh` 新增 **E 段权限审计**：任何 `o+w` 的文件/目录直接判失败。

**验证**：修完复检 `全局可写项: 0`，包内 `-rwsr-xr-x chrome-sandbox` / `-rwxr-xr-x qq-agent`。

### 4.2 rpm spec 缺 `Source0:` → `%{SOURCE0}` 不展开

**现象**：`tar (child): %{SOURCE0}: Cannot open: No such file or directory` —— 字面量被当成文件名。

**根因**：spec 里没有 `Source0:` 声明，`%{SOURCE0}` 宏未定义，rpm **不会报宏未定义**，
直接把原样字符串传下去。我以为"把 tar 放进 SOURCES/ 就够了"。

**修法**：spec 加 `Source0: $SOURCE_TAR`。

### 4.3 rpm 的 `%files` 指向一个不存在的目录

**现象**：文档文件是我在 `04-build-deb.sh` 里临时生成的，而 rpm 是**从 stage 树**打的，
看不到那个临时目录 → `%files` 列 `/usr/share/doc/qq-agent` 必然失败。

**修法**：把文档与许可说明的生成**下沉到 `03-stage.sh`**（`usr/share/doc/qq-agent/README`
+ `copyright`），deb 与 rpm **共用同一份**。`04-build-deb.sh` 改为只做存在性断言。

### 4.4 ★ Electron 完全没有完整性校验（供应链缺口）

**现象**：`verify_sha256` 只用在 SnowLuma 上。`ensure_electron()` **一个校验都没有** ——
供应链上任何一环被替换都发现不了。

**修法**：补上两个架构的官方 SHA256 pin（来源与交叉验证见 §6），并加 `require_electron_sha256()`，
与 SnowLuma 同策略：未核对就**硬失败**。

### 4.5 bash 的 `local` 展开时机陷阱 → 冒烟报告一行都写不出来

**现象**：`test/_smoke-common.sh: line 411: rest: unbound variable`，报告表格只剩表头。

**根因**：写成了
```bash
local st="${r%%|*}" rest="${r#*|}" nm="${rest%%|*}" dt="${rest#*|}"
```
bash 在执行 `local` **之前**就把整行所有 `${...}` 展开，于是 `nm`/`dt` 用到的 `rest`
此刻还没赋值 → `set -u` 直接让报告子 shell 死掉。

**修法**：**先声明、后赋值**分两句写。并全工程扫了一遍同款写法（另 7 处引用的是位置参数，
安全）。这条已写进代码注释。

### 4.6 `/mnt/f` 不支持 `chmod` → 必须在 ext4 上构建

**现象**：`/mnt/f` 上 `chmod 755` 后 `stat` 仍是 `777`；WSL home（ext4）上正常。

**结论**：**构建必须在 ext4 的工作副本里做**（`~/qqa-build`），产物再拷回 Windows。
在 `/mnt/f` 上直接构建会得到权限位全面失真的包。

### 4.7 ★ AppRun 的沙箱判据：本地全绿，真实使用却会致命

**现象**：AppImage 冒烟第一次跑出「31 通过 · 0 失败 · **1 警告**」。那条警告是
"日志里没看到降级提示"，同时静态检查报「AppImage 内 chrome-sandbox 仍带 setuid 位」。

**根因**：AppRun 原先用 `[ -u "$f" ]`（**文件模式位**）判断 Chromium 沙箱能否用。但：

- **真实使用**：AppImage 经 **FUSE 挂载，而 FUSE 挂载默认带 `nosuid`** ——
  文件上的 setuid 位还在，内核却忽略它 → 沙箱实际失效 →
  而 `-u` 仍为真 → AppRun **不会**加 `--no-sandbox` → **Chromium 直接启动失败**。
- **本地测试**：`APPIMAGE_EXTRACT_AND_RUN=1` 把载荷解到普通文件系统、位又保住了 →
  `-u` 为真且沙箱确实可用 → **恰好绕过了这个缺陷**。

也就是说：**测出来是绿的，真实场景是红的**。这类问题最容易被"测试通过了"骗过去。

**修法**：判据改成三条**同时**成立才算沙箱可用 ——
1. 文件有 setuid 位；
2. **属主是 root**（Chromium 的硬要求）；
3. **所在挂载点不含 `nosuid`**（读 `/proc/mounts`，取最长匹配的那个挂载点）。

**验证**：改完后冒烟从"1 警告"变成 **0 警告 / 31 通过**，并明确报出
`✓ 沙箱不可用时如实提示并降级 --no-sandbox`。

> ⚠️ 同一轮里第二次被**自己的陈旧断言**误导：第一版断言写死了旧提示文案
> （`AppImage 通过 FUSE 挂载`），AppRun 改了措辞之后断言就失效了 ——
> **降级明明发生了，却报"没看到提示"**。
> 所以最终把断言改成**按沙箱实际状态决定该不该期待提示**，而不是匹配某段固定文字。

### 4.8 ★ 沙箱判据里的 awk 也有 bug：根挂载点永远匹配不上

**背景**：§4.7 修好判据之后，端到端冒烟只覆盖到「属主不是 root」那一支 ——
而**真实场景会出事的是 `nosuid` 那一支**。既然端到端够不到，就
**把 AppRun 从已构建的产物里抠出来做单元测试**
（`test/40-apprun-sandbox-test.sh`，测的是**真正发货的代码**，不是源码的副本）。

**第一次跑就同时抓到两件事**：

1. **我的测试写错了**：把「普通文件系统」的夹具放在 `/tmp` ——
   而**本 WSL 的 `/tmp` 本身就是 `nosuid`**（`/tmp rw,nosuid,nodev,size=3985232k`）。
   所以正向对照返回 INEFFECTIVE 是**正确的**，错的是我的期望值。
2. **函数里确实有 bug**：`awk` 用 `index(d, mp "/")` 判断路径是否落在挂载点下 ——
   当挂载点是 `/` 时拼出来是 `"//"`，**根挂载点永远匹配不上**。
   实测 `/home/kmy` 取到的是**空串**。
   影响：根挂载点若带 `nosuid` 就检测不出来；更普遍地，根文件系统上路径的挂载选项恒为空。

**修法**：`pfx = (mp == "/") ? "/" : mp "/"`。

**验证**：修完单元测试 **6/6 全过**，含那条端到端够不到的 nosuid 分支：

| 用例 | 期望 | 说明 |
|---|---|---|
| 无 setuid 位 | INEFFECTIVE | |
| 有 setuid 位但属主非 root | INEFFECTIVE | 端到端也只覆盖到这一支 |
| 文件不存在 | INEFFECTIVE | 判据在异常输入下不能崩 |
| setuid + 属主 root + 非 nosuid | **EFFECTIVE** | **awk 修复前这条是红的** |
| **★ setuid + 属主 root + nosuid** | **INEFFECTIVE** | **真实 FUSE 场景，端到端够不到** |
| setuid + 属主 root + `/tmp` | INEFFECTIVE | /tmp 本就是 nosuid（数据点） |

> 顺带记住一条环境事实：**`/tmp` 在很多系统上是 `nosuid`**。
> 以后写「需要 setuid 生效」的测试时，别拿 `/tmp` 当"普通文件系统"——
> 这个坑第一次就把我引向"函数有 bug"的错误结论（其实函数是对的，是我的前提错了）。

### 5.1 ★ rpmbuild 不支持跨架构构建 —— arm64 rpm 必须在 aarch64 宿主上打

```
$ rpmbuild -bb --target aarch64 ...
Building target platforms: aarch64
error: No compatible architectures found for build
```

**这是 rpmbuild 内置的硬性架构保护（`checkBuildArch`），不是配置写法问题。**
实测对照：**同一个 spec 只把 `BuildArch` 换成宿主架构（x86_64）就成功，换回 aarch64 必失败。**

以下办法**全部试过、全部无效**：
`--target` / `_host_cpu` / `_build_cpu` / `_target_cpu` / `_host` / `_target_platform` /
私有 rpmdb + `--initdb` / `__os_install_post %{nil}`。
**★ 第 3 轮复核与更正**：本文前一版写「查过 `/usr/lib/rpm/rpmrc`：只有 `archcolor` 表，
没有可扩展的 arch-compat 表」—— **这句话是错的**，起因是 `grep ... | head -15` 被截断，
我只看到了文件开头那段 `archcolor`。实际 rpmrc 有 **99 条 `buildarch_compat:`** 与
**104 条 `arch_compat:`**（aarch64 的条目是 `buildarch_compat: aarch64: noarch`）。

据此第 3 轮补做了实验，逐一验证「补表能不能放行」：

| 试法 | 结果 |
|---|---|
| `/etc/rpm/rpmrc` 写入 `buildarch_compat: aarch64: x86_64` | ❌ 仍失败 |
| 直接给 `/usr/lib/rpm/rpmrc` 追加同一行（带备份） | ❌ 仍失败 |
| 再追加 `buildarch_compat: arm64: x86_64` 别名 | ❌ 仍失败 |

**结论不变但依据更硬**：rpm 6 的这个检查**并不查 rpmrc 的这两张表**，
所以补表这条路是死的。实验后已把 rpmrc 还原（残留自定义条目 0）。

`/usr/lib/rpm/platform/aarch64-linux/` 里只有 `macros`，也没有可加的兼容声明。

**★ 第 3 轮的解决路径（已验证可行）**：既然本工程是**纯重打包**（不含任何编译，
所有二进制都来自官方预编译产物），就可以用 **qemu-user + binfmt + arm64 rootfs**
造一个真正的 aarch64 用户态环境，在里面用**原生的 aarch64 rpmbuild** 构建。
这不是"绕过检查"，而是**真的换到 aarch64 环境里构建** —— 与容器 buildx
跨架构构建同一原理。**结果：`qq-agent-0.4.4-1.aarch64.rpm` 已成功产出（见 §1 与 §5.3）。**

前置条件（都已验证）：`qemu-user-binfmt` 注册成功（`qemu-aarch64` enabled）、
`ports.ubuntu.com` 可达（HTTP 200）。注意包名已从 `qemu-user-static` 改为
**`qemu-user`**（描述里写 "static binaries"）—— 第 2 轮按旧包名查到"无候选版本"，
**那个结论是错的**，实际可以直接装。

**对比：deb 没有这个限制** —— `dpkg-deb` 可以在 x86_64 上产出 arm64 的 `.deb`（本工程已产出）。
`Architecture:` 只是一个元数据字段，归档格式与宿主架构无关。

**最省事的做法**：用**原生 aarch64 宿主**打 arm64 的 rpm —— 本工程的 CI 用的正是
`ubuntu-24.04-arm`，那边属原生构建，没有这个问题。本地没有 ARM 机器时，
用 §5.3 的 qemu 方案也能产出。

`05-build-rpm.sh` 现在会对跨架构情形给出**清晰的解释并 exit 1**，而不是丢一句
`No compatible architectures` 让人对着发呆。

### 5.3 ✅ arm64 rpm 的实际构建方式：qemu-user + binfmt + arm64 rootfs

**结论：可行，已成功产出 `qq-agent-0.4.4-1.aarch64.rpm`（115.0 MB，546 文件）。**

**为什么这样是正当的**：本工程**不含任何编译**——所有二进制（Electron、SnowLuma、
原生 addon）都来自官方预编译产物，构建脚本只做「复制 + 打补丁 + 打包」。
因此在模拟环境中执行 aarch64 的 `rpmbuild` 不会引入任何"模拟出来的假结果"：
它产出的包内容与在真机 aarch64 上构建的完全一致（模掉 rpm 自带的构建时间戳）。
这与容器 buildx 的跨架构构建是同一原理。

**步骤**（脚本：`_ql_wsl_make_armroot.sh` + `_ql_wsl_build_arm64_rpm_chroot.sh`）：

1. `sudo apt-get install -y qemu-user qemu-user-binfmt mmdebstrap`
   —— 装完 `qemu-aarch64` 的 binfmt handler 自动注册并 enabled
   （实测跑 arm64 的 electron 会报 `Could not open '/lib/ld-linux-aarch64.so.1'`，
   证明 qemu **确实拦下了 aarch64 ELF**，只是缺 aarch64 的 libc）
2. `sudo mmdebstrap --architectures=arm64 --components=main,universe \
    --variant=apt --include=rpm,cpio,gzip,tar,coreutils,bash,gawk,... \
    resolute ~/armroot http://ports.ubuntu.com/ubuntu-ports`
   —— 156 MB，约 3.5 分钟。mmdebstrap 自己会提示
   "arm64 cannot be executed natively, but transparently using qemu-user binfmt emulation"
3. 验证 chroot 内环境 —— **这是关键**：
   ```
   uname -m : aarch64        ← qemu 正确伪装了 uname，所以构建脚本的跨架构检查会放行
   dpkg arch: arm64
   rpm      : RPM version 6.0.1
   rpmbuild : /usr/bin/rpmbuild
   ```
4. `sudo mount --bind ~/qqa-build ~/armroot/build`
   （stage 树仍在**宿主**上组装 —— 那一步只用 dpkg/tar，不需要 aarch64 环境）
5. `sudo chroot ~/armroot /bin/bash -c 'cd /build && bash scripts/05-build-rpm.sh --arch arm64'`

**代价与注意**：
- gzip 压缩 153 MB 的 SOURCE 在模拟下较慢，整个构建约 15–20 分钟
- chroot 内以 root 身份创建的产物会带 root 属主，需在宿主上 `chown` 回来
- rootfs 占 156 MB，保留着可随时重建

> **CI 不需要这套东西**：GitHub Actions 的 `ubuntu-24.04-arm` 是**原生** aarch64 机器，
> `rpmbuild` 在那边是原生构建。qemu 方案只是让"没有 ARM 机器"的本地环境也能产出产物。

### 5.5 AppImage 跨架构：**不需要 qemu**（与 rpm 的做法形成对照）

三种包格式在"跨架构构建"上的差别很有意思，值得记下来：

| 包格式 | x86_64 上能否产出 arm64 包 | 原因 |
|---|---|---|
| `.deb` | ✅ 直接可以 | `dpkg-deb` 不校验宿主架构；`Architecture:` 只是元数据 |
| `.rpm` | ❌ 不行 → 需 **qemu + arm64 rootfs** | rpmbuild 有硬性 `checkBuildArch` 保护 |
| `.AppImage` | ✅ 直接可以 | `appimagetool` 只做「拼装 + 调 mksquashfs」，**不执行目标架构的代码** |

**AppImage 的具体做法**：用**宿主架构的 appimagetool** + **目标架构的 runtime**
（`--runtime-file`），并设 `ARCH=<目标架构>`。runtime 的架构会被脚本单独断言，
所以不会出现"工具跑错架构"这种静默错误。

**附带发现（对验证很有用）**：AppImage 的 SquashFS 偏移**恰好等于 runtime 文件的字节数**
（实测：x86_64 产物 `--appimage-offset` 报 `944632` == `runtime-x86_64` 的大小）。
因此**跨架构时不必执行目标架构的 runtime**，也能用
`unsquashfs -o <runtime大小>` 把载荷读出来验证。
这一条已写进 `06-build-appimage.sh` 的自检：先试 `--appimage-extract`，
失败则退到 `unsquashfs -o`；两条都不行就**拒绝交付**（不允许"没验证过就发"）。

**踩到的坑**：WSL 里 binfmt 的 qemu 注册**每次 WSL 重启就丢**。
第一次打 aarch64 AppImage 时报 `cannot execute binary file: Exec format error`，
就是这个原因（当时仍按旧思路用目标架构的 appimagetool）。
改成"宿主工具 + 目标 runtime"之后，这条路**彻底不依赖 qemu**，也就不受它影响。
