# 05 · arm64 施工方案（无 ARM 机器条件）

> 写于：2026-09-27
> 前置阅读：`02-构建方案.md`（打包设计）、`03-交接文档.md`（交接入口）、`04-技术笔记-SnowLuma与Electron.md`（硬约束）
> 本文件回答一个问题：**手里没有 ARM 电脑，arm64 版能不能做、怎么做。**

---

## 0. 一句话结论

**能做。** 而且这个工程恰好属于「没有对应架构机器也能做」的那一类——
因为它是**装配型**打包，不是**编译型**打包。

| 环节 | 需不需要 ARM 硬件 | 说明 |
|---|---|---|
| 组装应用树 | ❌ 不需要 | 复制文件 + 打文本补丁 |
| 下载 arm64 运行时 | ❌ 不需要 | Electron / SnowLuma 官方都有 arm64 预编译产物 |
| 生成 `.deb` / `.rpm` | ❌ 不需要 | 架构字段只是元数据字符串，x86_64 主机上就能产出 arm64 包 |
| 静态校验（架构/依赖） | ❌ 不需要 | `file` / `readelf` / `ldd` / `dpkg-deb -I` |
| **真实冒烟测试** | ✅ **需要** | Electron 得真跑起来，只有这一步躲不掉 |

**验证路线已定：GitHub Actions 原生 arm64 runner（`ubuntu-24.04-arm`）。**
它是真 ARM CPU（不是模拟），公开仓库免费，可重复、可留证。

## 1. 可行性依据（已核实的事实，不是推测）

### 1.1 本应用**没有需要交叉编译的东西**

实测 `resources/app/package.json` 的依赖清单——只有三个：

```json
{ "js-yaml": "^5.4.1", "undici": "^6.28.0", "ws": "^8.18.0" }
```

**全是纯 JS，零原生扩展。** 再对整棵 `node_modules/` 递归搜 `*.node`，
除 `snowluma/` 自带的那几个之外，**一个都没有**。

> 这条是整个方案成立的关键。如果依赖里有 `better-sqlite3` / `sharp` / `node-gyp` 那类东西，
> 就得为 arm64 交叉编译或找预编译包，工作量完全是另一个量级。**这里没有。**

### 1.2 三个平台相关件，全部「下载即得」

| 组件 | arm64 来源 | 状态 |
|---|---|---|
| Electron 33.4.11 | `electron-v33.4.11-linux-arm64.zip`（官方 release，与 x64 同版本号同步发布） | ⬜ 待下载核对 SHA256 |
| SnowLuma 1.14.19 | `SnowLuma-v1.14.19-linux-arm64.tar.gz`（**45,817,799 B**，见 `01-当前进展.md` §3.1） | ⬜ 待重核 SHA256 |
| ffmpeg | **SnowLuma 自带 `native/ffmpeg/` addon**，不是独立二进制 | ✅ **命名已查清**：`ffmpegAddon.<platform>.<arch>.node`（x64 实测为 `ffmpegAddon.linux.x64.node`）→ arm64 应为 `ffmpegAddon.linux.arm64.node`，已由 `test/05-arch-audit.sh` 断言存在 |

SnowLuma 官方 release 原文（`01-当前进展.md` 已摘录）：
> *"跨平台正式支持：Windows x64、Linux x64 与 Linux arm64 均可完整运行 SnowLuma。"*

### 1.3 deb / rpm 的架构是「声明」，不是「编译结果」

- `.deb` 的架构来自 `DEBIAN/control` 里的 `Architecture: arm64`
- `.rpm` 的架构来自 `rpmbuild --target aarch64`

两者在 x86_64 主机上都能正常产出，`dpkg-deb --build` / `rpmbuild` **不校验宿主 CPU**。
（`rpmbuild` 只会在你把纯二进制包标成 `noarch` 时才报错。）

## 1.4 ★ 已解决：SnowLuma 配置/数据目录怎么重定向

> 这是 `03-交接文档.md` §8 的**头号开放问题**，原本阻塞 stage 阶段。
> 2026-09-27 解包 `SnowLuma-v1.14.19-linux-x64.tar.gz` 后实测查清，并已实现为第 10 个补丁。

**结论一句话：`config/` 与 `data/` 是「相对 cwd」的纯相对路径，没有任何环境变量可覆盖；
而原生件是按模块路径（`import.meta.url`）解析的，与 cwd 无关。
所以正确做法是「换工作目录」，不是去找环境变量——找也找不到。**

证据（均为实际读码所得，非推测）：

| 项 | 证据位置 |
|---|---|
| config 目录是硬编码相对名 | `logger-BAozzyTt.js:88`、`config-CEQwQxHY.js:26,761,10657`、`server-D1_OR83N.js:3453,3773,4084` → 均为 `var CONFIG_DIR = "config";` |
| data 目录同理 | `index.mjs:229997` `static openForUin(uin, dataRoot = "data")`；`:232285` 调用时**不传**该参数 → 取默认相对值 |
| 写入点 | `server-D1_OR83N.js:13674` `mkdirSync("config", { recursive: true })` |
| **没有**可用的覆盖变量 | 全量 grep 只找到 `SNOWLUMA_LOG_DIR` / `SNOWLUMA_WEBUI_*` / `SNOWLUMA_HOOK_RUNTIME_DIR` / `SNOWLUMA_TELEMETRY` 等，**不存在** CONFIG_DIR / DATA_DIR 类变量 |
| 原生件与 cwd 无关 | `index.mjs:226463` `path.resolve(__dirname, "native")`、`:4857` `path.resolve(__dirname$1, "native", "ffmpeg")` → 均由 `import.meta.url` 派生 |
| cwd 的实际来源 | `src/app.js` 用 `spawn(nodeExe, [indexMjs], { cwd: dir })` 拉起，`dir` 就是只读的 `/opt/qq-agent/resources/app/snowluma` |
| 应用自己也读它 | `src/app.js:161,176` 读 `<dir>/config/runtime.json`；`:709` 扫 `<dir>/config/onebot_*.json` |

### 对策：符号链接镜像目录（第 10 个补丁 `snowluma-runtime-mirror`）

只改 **`snowlumaDir()` 一个函数**：在 Linux 上返回用户主目录下的
`~/.local/share/qq-agent/snowluma/`「符号链接镜像目录」——
静态件（`index.mjs` / `*.js` / `native/` / `node` / `client/`）软链回只读安装目录，
`config` / `data` / `logs` **刻意不软链**，留给 SnowLuma 在镜像里自行创建。

**为什么只改一处而不是逐个打补丁**：`snowlumaDir()` 是
`spawn` 的 cwd、`runtime.json` 读取、`onebot_*.json` 令牌扫描
**三处（共 4 个引用点）共同的入口**。逐个改要动 4 处，漏一处就是隐性故障
（例如只改了 cwd 却没改 runtime.json 读取 → SnowLuma 能跑，但 WebUI 端口和
地址探测全部失灵，表现为"能登录但打不开 WebUI"这种极难查的现象）。
改入口则三处自动一致。

**副产品收益**：`/opt` 保持完全只读，运行期数据全在用户主目录——
与本方案「程序与数据分离」的设计原则一致，卸载也不会丢数据。

**验证状态**：锚点唯一性 10/10 命中、真打 10/10 成功、幂等复打 10/10 跳过、
三个改动文件 `node --check` 通过（本地实测，见 §7 阶段 2）。
**运行时行为仍需在真 Linux 上冒烟确认**（Windows 上建符号链接需要特权，无法本地验证）。

## 2. 目标平台与命名规范（在 `02-构建方案.md` §7 基础上扩展）

| 项 | x86_64 | **arm64（新增）** |
|---|---|---|
| deb `Architecture:` | `amd64` | **`arm64`** |
| rpm `--target` | `x86_64` | **`aarch64`** |
| deb 产物名 | `qq-agent_0.4.4_amd64.deb` | **`qq-agent_0.4.4_arm64.deb`** |
| rpm 产物名 | `qq-agent-0.4.4-1.x86_64.rpm` | **`qq-agent-0.4.4-1.aarch64.rpm`** |
| AppImage 产物名 | `QQ-Agent-0.4.4-x86_64.AppImage` | **`QQ-Agent-0.4.4-aarch64.AppImage`** |

> ⚠️ 注意大小写和拼写差异：**deb 系用 `arm64`，rpm 系用 `aarch64`**。
> 写成 `arm64` 的 rpm 装不上，写成 `aarch64` 的 deb 也装不上。这是最常见的低级错误。

**目标发行版**：Debian / Ubuntu arm64、RHEL 系 arm64、
以及 Raspberry Pi OS **64 位**（`armhf` 32 位不在范围内——Electron 不支持 32 位 ARM）。

## 3. 代码改动清单（全部是**新增参数**，不改变 x86_64 行为）

### 3.1 设计原则

**一份代码出两个架构。** 绝不复制一份 `*-arm64.sh` 平行维护——
否则将来改一处补丁要改两遍，必然分叉。

统一约定：所有脚本接受 `--arch x86_64|arm64`，**缺省值 `x86_64`**，
保证现有 x86_64 流程一字不改、行为完全不变。

### 3.2 `scripts/lib.sh`（参数化核心）

| 变量 | x86_64 | arm64 |
|---|---|---|
| `ARCH` | `x86_64` | `arm64` |
| `DEB_ARCH` | `amd64` | `arm64` |
| `RPM_ARCH` | `x86_64` | `aarch64` |
| `ELECTRON_ARCH` | `x64` | `arm64` |
| `SNOWLUMA_ARCH` | `x64` | `arm64` |

并相应改：
- `ensure_electron()` / `ensure_snowluma()` 的 cache 路径与解包目录**带架构后缀**
  （`cache/electron-v33.4.11-linux-arm64/`、`cache/snowluma-linux-arm64/`），
  两个架构的 cache **必须能共存**，不能互相覆盖
- 新增 `assert_arch_triplet()`：断言 `ARCH/DEB_ARCH/RPM_ARCH` 三者组合合法，
  防止手改出 `arm64` + `amd64` 这种混搭

### 3.3 `scripts/01-extract.sh`

按 `--arch` 选下载 URL 与 SHA256，**两个架构各一份 SHA256 常量**（不能共用）。
下载后校验，失败即中止。cache 命中则跳过（保持现有幂等语义）。

### 3.4 `scripts/03-stage.sh`（尚未编写 → 直接按架构维度设计）

**这是最需要小心的一步。** 两个必须遵守的规则：

**规则 1：`snowluma/` 整棵替换，绝不在 Windows 树上打补丁。**
源头 `E:\...\resources\app\snowluma\` 里是 Windows 原生件（§4 坑 A 有实测清单）。
arm64 版的 `snowluma/` 必须**完全来自官方 arm64 tarball**，
一个字都不从 Windows 树继承（配置/数据目录例外——那些本来就该排除）。

**规则 2：应用代码与运行时分离。**

推荐给 `03-stage.sh` 加一个附加模式，供 CI 使用：

```bash
bash scripts/03-stage.sh --arch arm64                        # 本地：完整组装
bash scripts/03-stage.sh --app-tarball                       # CI：只产出清洗过的应用代码 tar
```

- `--app-tarball`：复制 `resources/app` → 套 `EXCLUDE_PATTERNS` → 打 Linux 补丁
  → 打成一个 tar（**平台无关**），供 CI 取用
- CI 侧：拿这个 tar + 下载 arm64 的 Electron/SnowLuma → 组装

**为什么必须分离**：CI 里**没有 `E:\` 盘**。GitHub runner 是全新容器，
拿不到你本机已安装的 V0.4.4 应用树。这一步不想清楚，workflow 一定跑不起来。

> 替代设计（更干净但改动更大）：拆成 `03-stage-app.sh` + `03-stage-runtime.sh` + `03-stage.sh`（编排）。
> 如果将来还想支持第三个架构，建议直接上这个结构。**当前两架构用 `--app-tarball` 模式够了。**

### 3.5 `scripts/04-build-deb.sh` / `05-build-rpm.sh`

- `04`：`DEBIAN/control` 写 `Architecture: $DEB_ARCH`
- `05`：`rpmbuild --target $RPM_ARCH`，`.spec` 里 `BuildArch: $RPM_ARCH`
- 依赖名映射表**两个架构共用**（`libgtk-3-0` 等在 arm64 上同名，无需分叉）
- 产物名按 §2 的表

### 3.6 `scripts/06-build-appimage.sh`

仍**最后做**（用户红线，见 `03-交接文档.md` §7）。
只需在取 Electron 时按架构走，其余逻辑不变。
产物名 `aarch64`（AppImage 社区惯例用 `aarch64`，不是 `arm64`）。

### 3.7 新增 `test/05-arch-audit.sh`（★ 本方案最有价值的一个新增）

**架构审计脚本。** 在打包**之前**扫一遍 stage 树，命中就失败：

```bash
# 伪代码，实现时用 od 读魔数（不依赖 file 命令是否安装）
#   ELF = 7f 45 4c 46   → 必须 readelf -h 显示 AArch64
#   PE  = 4d 5a (MZ)    → 直接判定失败（Windows 二进制混入）
```

三类断言：
1. 树里**所有 ELF** 的 `Machine` 必须是 `AArch64`（发现 `Advanced Micro Devices X86-64` 即失败）
2. **不允许出现任何 PE（MZ）文件**——`snowluma/native/*.win32.x64.node` 这类鬼东西一露面就拦下
3. `snowluma/native/` 下的 arm64 原生件（`*.node` / `*.so`）**必须存在**（存在性断言，防空包）

> 这个脚本把「坑 A」从"要记得小心"变成"机器强制检查"。
> 人工小心会失效，脚本断言不会。**优先级排在打包脚本之前。**

### 3.8 新增 `.github/workflows/build-linux-arm64.yml`

见 §5.3 草案。

## 4. 硬约束与坑（arm64 专属）

### 坑 A：Windows 原生件混入 —— 实测清单 ★最要命

我在本机应用树里实测到这些文件（`$app/snowluma/native/`）：

```
snowluma/native/snowluma-win32-x64.dll              248,832 B
snowluma/native/snowluma-win32-x64.node             306,688 B
snowluma/native/websocket-win32-x64.node            163,328 B
snowluma/native/ffmpeg/ffmpegAddon.win32.x64.node 6,511,104 B
```

**这就是"照原样复制 app 树"会踩的雷**：包里会塞进 4 个 Windows 二进制，
arm64 Linux 上一个都加载不了，而且 `dpkg-deb` 不会报任何错——
装完启动才发现问题，很难查。

**对策**：`snowluma/` 整棵用官方 arm64 包替换（§3.4 规则 1） + `test/05-arch-audit.sh` 强制拦截（§3.7）。

**✅ 已查清（2026-09-27）**：`ffmpeg` 是以 **SnowLuma 自带 addon** 形式存在的，
文件名规则来自 `index.mjs:4852` 的 `addonFileName()`：

```js
`ffmpegAddon.${process.platform}.${process.arch}.node`
```

x64 包实测为 `native/ffmpeg/ffmpegAddon.linux.x64.node`，故 arm64 应为
`native/ffmpeg/ffmpegAddon.linux.arm64.node`。
**`test/05-arch-audit.sh` 已把这一项做成硬断言**（缺了直接拒绝打包），
不再依赖"记得人工去看一眼"。

### 坑 B：`libasound2` / `libasound2t64` 的发行版差异

`02-构建方案.md` §3.2 已记录：Debian 13 / Ubuntu 24.04+ 是 `libasound2t64`。
这在 arm64 上和 amd64 上**是一样的规则**（同名），所以依赖映射表不用分叉。

但 arm64 的现实是：**很多 arm64 设备跑的是树莓派 OS（Debian 12/13）**，
老版本那边还是 `libasound2`。所以 `libasound2 | libasound2t64` 的备选写法
**在 arm64 上比在 amd64 上更重要**，不能偷懒只写一个。

### 坑 C：树莓派必须 64 位系统

- 树莓派 4/5 装**64 位** Raspberry Pi OS → 可用
- 树莓派 2 / Zero / 老 3 装 32 位（armhf）→ **Electron 直接不支持**，无解
- 判断方法：`uname -m` 输出 `aarch64` 才是对的，`armv7l` 说明装错了系统

### 坑 D：CI 环境与本地环境的差异

| 差异点 | 影响 | 对策 |
|---|---|---|
| runner 上没有 `E:\` 应用树 | 拿不到基线代码 | §3.4 的 `--app-tarball` 模式 |
| runner 上无显示服务 | Electron 起不来 | `xvfb-run`（与现有测试设计一致） |
| runner 上 `sudo` 免密 | 可以真装真卸 | 正好，冒烟测试按原设计跑 |
| `chrome-sandbox` 需 setuid root | 权限位易丢 | 装完 `chown root:root && chmod 4755`，测试中另跑一遍 `--no-sandbox` 对照 |
| runner 每次全新 | 不可复现的隐性依赖 | 所有步骤写进脚本，不在 shell 里手敲 |

### 坑 E：不要把 qemu 的通过当成"能用"

若将来走 qemu-user-static（WSL2 里 `binfmt_misc`）做本地验证——
Chromium/Electron 带 JIT 和 seccomp，**qemu 下大概率闪退**。
它的正确用途只有一个：**验证静态依赖齐不齐**（`ldd` 无 `not found`、二进制能加载）。
**绝不能拿 qemu 结果当冒烟测试结论。** 本方案选了原生 runner，就是为了绕开这个坑。

## 5. 验证路线：GitHub Actions 原生 arm64 runner

### 5.1 为什么选它

| 维度 | 说明 |
|---|---|
| 真实性 | **真 ARM64 CPU**，不是模拟，冒烟结论有效 |
| 成本 | 公开仓库**免费**；私有仓库按 GitHub 计费规则扣分钟（倍率见 GitHub 文档） |
| 可复现 | workflow 是代码，改了什么、跑了什么全留证 |
| 留证据 | 构建日志 + 产物 artifact 可直接下载，满足"测试无误"的验收要求 |
| 缺点 | 需要把（清洗过的）应用代码放到仓库或不落地带到 CI，涉及§5.4 的安全约束 |

### 5.2 runner 名称

```yaml
runs-on: ubuntu-24.04-arm     # 原生 arm64；备选 ubuntu-22.04-arm
```

> ⚠️ **不要**写成 `runs-on: ubuntu-latest` 再指望交叉编译。
> `ubuntu-latest` 是 x86_64，在上面**跑不了** arm64 的 Electron，
> 冒烟测试那一环会以"Exec format error"告终。

### 5.3 workflow 草案（待评审后落地）

```yaml
name: build-linux-arm64

on:
  workflow_dispatch:          # 手动触发（主用）
  push:
    tags: ['v*-arm64']

jobs:
  arm64:
    runs-on: ubuntu-24.04-arm
    steps:
      - uses: actions/checkout@v4

      - name: 装打包工具链
        run: |
          sudo apt-get update
          sudo apt-get install -y dpkg-dev fakeroot rpm cpio xvfb \
            desktop-file-validate file libarchive-tools

      - name: 取回清洗过的应用代码树
        # ★ 见 §5.4：这一步的数据来源是安全红线，二选一
        run: |
          mkdir -p stage-src
          tar -xzf ./ci-input/app-code.tar.gz -C stage-src

      - name: ★ 隐私红线复检（命中即失败）
        run: bash scripts/99-selfcheck.sh --input ./stage-src

      - name: 下载并解包 arm64 运行时
        run: bash scripts/01-extract.sh --arch arm64

      - name: 组装应用树
        run: bash scripts/03-stage.sh --arch arm64 --app-src ./stage-src

      - name: ★ 架构审计（x86_64 / PE 混入即失败）
        run: bash test/05-arch-audit.sh --arch arm64

      - name: 打 deb / rpm
        run: |
          bash scripts/04-build-deb.sh --arch arm64
          bash scripts/05-build-rpm.sh --arch arm64

      - name: 静态校验产物
        run: |
          dpkg-deb -I out/qq-agent_0.4.4_arm64.deb
          rpm -qp --qf '%{ARCH}\n' out/qq-agent-0.4.4-1.aarch64.rpm

      - name: 真实安装 + 冒烟测试
        run: |
          sudo dpkg -i out/qq-agent_0.4.4_arm64.deb || sudo apt-get -f install -y
          sudo bash test/10-deb-smoke.sh --arch arm64

      - name: 卸载清理验证
        run: sudo bash test/15-uninstall-check.sh

      - uses: actions/upload-artifact@v4
        with:
          name: qq-agent-arm64-${{ github.run_number }}
          path: out/*
          retention-days: 30
```

**待定项**（落地前必须定）：

### 5.4 ★ 安全红线：什么东西可以进 CI

这是本方案**唯一的真正风险点**，必须说清楚。

`03-交接文档.md` §7 记录得很明确：构建基线（`resources/app`）里
**混着线上机器人的隐私数据**：

```
snowluma/data/<QQ号>/snowluma_identity.db   ← 登录态
snowluma/data/<QQ号>/messages.db            ← 私聊消息库
snowluma/config/runtime.json               ← WebUI 令牌
snowluma/logs/*.log                        ← 含 QQ 号、群号、消息片段
data/config.json                           ← API Key 明文
community.key                              ← 厂商名单写权限密钥
```

**结论：绝对不能把原始 `resources/app` 整棵推上 GitHub**（哪怕私有仓库，
也不该把登录态和私聊库传上第三方存储）。

三个可选方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **(a) 私有仓库存清洗后的代码** | 跑 `03-stage.sh --app-tarball` 产出**已套 EXCLUDE_PATTERNS** 的代码树，提交到私有仓库，CI checkout | ✅ **推荐**。简单，且清洗动作在本地可控 |
| (b) artifact 中转 | 本地清洗 → 上传为 artifact → CI 下载 | ⚠️ 仍进 GitHub 存储，且流程绕 |
| (c) 自建 runner | 自己一台 arm64 机器挂进 Actions | ❌ 又回到"需要有 ARM 机器" |

**无论选哪个，必须同时满足两条硬约束**：

1. 清洗**在本地完成**（`EXCLUDE_PATTERNS` 由 `lib.sh` 统一提供，不是 CI 里临时拼）
2. CI 端**再复检一次**——上面前两个"★"步骤就是干这个的。
   复检失败**必须让构建红掉**，不能只打警告。

> 复检要断言至少这些路径**不存在**：
> `snowluma/data`、`snowluma/config`、`snowluma/logs`、`data`、
> `community.key`，以及任何 `*.db` / `*.dmp`。
> 建议再加一条：扫 `*.json` 里有没有形如 `sk-` 的 key 字面量。

### 7.1 真跑一遍才暴露的两个 bug（教训）

「静态检查全绿」不等于「能跑」。本轮坚持把 `03-stage.sh` 真跑一遍，抓到两个**只有
实际执行才会暴露**的问题 —— 记录在此，因为它们的模式会重演：

**bug 1：函数用 stdout 返回路径，而日志也写 stdout → 返回值被污染**

`lib.sh` 的 `ensure_electron()` 尾部用 `echo "$dir"` 返回路径，调用方写
`EDIR="$(ensure_electron)"`。但函数内部 `log "解包 Electron ..."` 也写 **stdout**，
于是捕获到的"路径"变成：

```
[36m[12:52:02][0m 解包 Electron 33.4.11 linux-x64 ...
/f/kmy/.../cache/electron-v33.4.11-linux-x64
```

紧接着 `cp -a "$EDIR"/.` 直接失败。**这个坑在 lib.sh 里潜伏已久**——原版
`01-extract.sh` 没捕获返回值，所以从没暴露；本轮改写后才踩响。

*修法*：`log` / `warn` / `ok` 一律改写 **stderr**（`die` 本来就是）。
并立下纪律：**任何「用 stdout 返回值的函数」内部都不许往 stdout 写诊断信息。**

**bug 2：架构审计把无害的 `.ico` 误判成 Windows PE → 假失败**

审计脚本原先用 `grep -E ': .*(PE32|MS Windows|MS-DOS)'` 判 PE。但 `file` 会把
`resources/app/assets/icon.ico` 报成 `MS Windows icon resource …`，
于是整个构建被一条无害的图标资源挡住。

*修法*：判据收窄到真正的 PE 可执行体 `PE32|MS-DOS executable`；
Windows 资源文件降级为**只提示不阻断**的警告。
并**立刻用正反用例复验**——确认"混入真 PE"仍然被拦截，而不是把防线削弱了。

**bug 3（我自己的测试写错，同样值得记）：测试因为错误的原因而"通过"**

给审计脚本写正反用例时，我把 `--root` 传成了夹具根目录，而它的语义是
**应用安装树**（含 `qq-agent`/`resources/` 的那一层）。结果用例 1 假失败，
而用例 4/5 是**因为错误的原因通过**——审计根本没看到 `native/` 目录，
"拦住"纯属巧合。**假绿比假红危险得多。**

*修法*：修正 `--root`，并让用例显式打印它实际断言到了什么。

> 三条的共同点：**都是"看起来对"的地方出错**。所以本工程的纪律是
> ——凡新增断言/脚本，必须用**正反用例**证明它既会拦错的、也会放过对的。
