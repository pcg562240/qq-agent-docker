## 三、关键发现

### 3.1 SnowLuma 官方**确实提供 Linux 原生版**（决定项目成败的一点）

原本这是最大的疑点：Windows 包里只有 `snowluma-win32-x64.node`、`snowluma-win32-x64.dll`、
`node.exe`、`launcher.bat`，看起来是纯 Windows 闭源二进制。

查证结果——官方 GitHub release **每个版本都发布 6 个产物**：

```
v1.14.19 (2026-09-21)
  SnowLuma-v1.14.19-linux-arm64-lite.tar.gz     4,127,246
  SnowLuma-v1.14.19-linux-arm64.tar.gz         45,817,799
  SnowLuma-v1.14.19-linux-x64-lite.tar.gz       4,102,982
  SnowLuma-v1.14.19-linux-x64.tar.gz           46,374,313   ← 本方案选用
  SnowLuma-v1.14.19-win-x64-lite.zip            4,770,883
  SnowLuma-v1.14.19-win-x64.zip                37,839,264
```

官方 release 原文：*"跨平台正式支持：Windows x64、Linux x64 与 Linux arm64 均可完整运行
SnowLuma，包含 QQ 接入、OneBot v11 与 WebUI 管理能力。"*

**范围外的好消息**：还有 **linux-arm64** 版。虽然本轮只做 x86_64（用户选定），
但将来要加 arm64 时，协议端这条路上没有障碍。

### 3.2 Windows 硬编码**极少** —— 这是最大的意外之喜

我原本预估要"重写"。实测全量搜索后，需要改的只有 **3 个文件、9 个点**：

```
src/app.js        → wmic, cmd.exe, launcher.bat, node.exe, QQ.exe, powershell
src/routes.js     → explorer.exe, cmd.exe
electron/main.js  → （无 Windows 专用调用；只有数据目录策略问题）
```

agent 核心（`src/` 下 40 个模块、1 MB 代码）**几乎全是跨平台 JS**：
ffmpeg 探测已经同时试 `ffmpeg` 和 `ffmpeg.exe`，路径分隔符处理也普遍用了兼容写法。
所以"重新编写成 Linux 版"实际是**薄薄一层适配**，不是重写。

### 3.3 数据目录是本方案最关键的架构问题

原版设计（`electron/main.js` 注释原文）：
> *"Kondius 钦定：所有数据都存在安装目录下，不往 `%APPDATA%` 塞。"*

Windows 上能跑（安装目录 ACL 允许写入），**Linux 上必然失败**：
deb/rpm 装到 `/opt/qq-agent`，属 root，普通用户写不进去 →
config 写失败 → 单实例锁写失败 → 启动即崩。

对策：`resolveDataDir()` 加 Linux 分支，走
`QQ_AGENT_DATA_DIR` > `${XDG_DATA_HOME:-~/.local/share}/qq-agent/data`。
保留 `data-<N>` 二次实例后缀（端口偏移逻辑依赖它）。

### 3.4 ★ 已安装的 app 树里混着用户隐私数据（安全红线）

核实"原始文件有没有被我改动"时，发现 `resources/app/snowluma/` 下有一批**运行期生成**的文件：

```
snowluma/data/2215188985/messages.db           ← ★ 私聊消息库
snowluma/data/2215188985/media.db
snowluma/data/2215188985/reactions.db
snowluma/data/2215188985/snowluma_identity.db  ← ★ 登录态
snowluma/config/runtime.json                   ← WebUI 令牌
snowluma/config.auto-20260924-181653/
snowluma/logs/snowluma-2026-09-24*.log         ← 含 QQ 号、群号、消息片段
```

这些是**线上那个正在跑的机器人**（QQ 2215188985）自己写的，不是我改的。

**风险**：`stage` 阶段如果照原样复制整棵 app 树，就会**把号主的登录态、私聊消息、
WebUI 令牌一起打进分发给别人的安装包**。另外 `data/config.json` 里是 **API Key 明文**。

**对策**：在 `scripts/lib.sh` 里定义 `EXCLUDE_PATTERNS`，把这些路径连同
`community.key` 一起排除。`03-stage.sh` 必须套用。**这条已列为红线。**

## 四、本轮踩到并修掉的坑（都已复测）

### 坑 1：PowerShell 吃掉内联 bash 的引号

`wsl -d Ubuntu -- bash -c "……含 for 循环和 $(...) 的长命令……"` 会语法报错，
甚至把 `/dev/null` 解析成 `F:\dev\null`。

**对策**：脚本一律写成 `.sh` 文件再 `bash 文件`。本轮所有脚本都遵守这条。

### 坑 2：CRLF 让 5 个补丁锚点全部失配 ★最有价值的一个

`patch-linux.mjs` 第一轮跑出 **5 处"锚点未找到"**，但关键字盘点明确显示代码存在。

用 `diag-anchors.mjs` 定位根因：
```
electron/main.js  行尾: CRLF=907  纯LF=0
src/app.js        行尾: CRLF=2494 纯LF=0
src/routes.js     （单行锚点，所以侥幸命中）
```
**Windows 侧的 app 树文件全部是 CRLF，而锚点写在源码里天然是 LF** → 必然 0 命中。

**对策**：`patch()` 里做行尾归一化——比对前把文件与锚点都转成 LF，
替换完再按原文件的主流行尾写回（CRLF 文件仍写 CRLF，不破坏原风格）。
修完 9/9 全部命中。

> 同一个坑**又踩了第二次**：`verify-anchors.mjs`（只读校验脚本）一度也漏了归一化，
> 于是报出 5 处**假失败**。这说明"逐行比对脚本必须归一化行尾"要当成本工程的通用纪律，
> 而不是某个脚本的局部修补。两个脚本现已一致。

### 坑 3：幂等判据被多个补丁共用 ★第二个有价值的

`routes.js` 上三个补丁原本共享标记 `QQA_LINUX_PATCH:open-with`。
第一次运行：都命中 → 第一个把标记写进文件 → 后两个再跑时被误判成"已打过"。

复测输出暴露了它：
```
===== 再打一遍验证幂等 =====
  [SKIP(已打过)] src/routes.js  ← routes-open-data-dir
! [FAIL(锚点未找到)] src/routes.js  ← routes-open-snowluma-dir
! [FAIL(锚点未找到)] src/routes.js  ← routes-open-webui
合计: 应用 0 · 跳过 7 · 失败 2      ← 应为「跳过 9 · 失败 0」
```

**对策**：`patch()` 支持**按补丁独立的幂等判据**（断言数组），
三个 routes 补丁各自用 `['openWith(DATA_DIR)']` / `['openWith(dir)']` /
`['openWith(webuiUrl)']`。复测变成 `跳过 9 · 失败 0`。

> 这两条正好印证了本项目交接文档里的老教训：
> *"`skipIf` 标记必须只可能出现在'修复后'的内容里……撞了就静默跳过，`node --check` 也看不出来。"*
> 本轮的补丁工具把"静默跳过"改成了"**报错中止**"，从机制上杜绝了这类问题。
